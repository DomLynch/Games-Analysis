Why PARTIAL: SpacetimeDB is a database engine. The only game code in the repo is the Blackholio demo, which has no drop table, no loot roll, no ownership, and no rarity. What it does have is an unowned pickup pool (food pellets) refilled to a fixed count on a timer and consumed by overlap; that is a pool-refill mechanism that belongs to spawns (row 23), and it gives mass, not loot. It is real and read, but thin for loot-drops.
Mechanism (short, read in full): spawn_food (540-568) runs every 500 ms (timer at 141); it returns early with no players (541); it refills while food_count < TARGET_FOOD_COUNT = 600 (20, 549-550); each pellet gets mass from gen_range(FOOD_MASS_MIN..FOOD_MASS_MAX) (18-19, 551), so the values are 2 or 3 because the Rust range is exclusive. Eating adds mass to the consumer (470) and deletes the food row (478).
Best transferable idea: a pickup pool that is topped up to a target count on a fixed timer, with each pickup's value drawn from a small range, keeps a zone stocked without a per-kill drop roll.
Decision (proposed): adapt. Use the refill-to-count shape for zone pickups and resource nodes as zone data (cap, interval, value range) under row 23, not as a loot system. Reject as a loot model: it has no drop table, no roll and no ownership, so it does not answer the loot question.
Acceptance (if built): a zone with a cap of N pickups refills to N on its interval after a player takes some, and a server test asserts the count never exceeds the cap.
