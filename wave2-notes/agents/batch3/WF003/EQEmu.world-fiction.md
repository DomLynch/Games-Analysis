## 1. What the player sees and feels
A guard or merchant card carries one attitude word on a nine-step ladder, from the top word for an ally down to the bottom word for a scowl. Each fight or quest reward nudges that standing, and the nudge ripples: one action moves the faction you earned and a few linked factions, some up and some down, each by a small amount. The same ripple reaches every player whose name is on the NPC's hate list, so a group of three that fought the same creature all see their standings move. Names come from the data with underscores and digits; the screen shows the clean word form. Each NPC can carry short emote lines for combat start, combat end, death, after-death, hail, a kill of a player, a kill of an NPC, spawn and despawn; the line can name the NPC or its race and class. At 375 wide, a nine-word ladder and a three-row ripple toast fit on one card.

## 2. Why it works / is striking
- Readable at 375 wide: yes. The ladder is one word per card, and the ripple is two to three short rows.
- One signature behaviour: the ripple. One action moves a web of linked standings, and the player sees the web move. Small multipliers (0.05 to 0.35 in the association data) mean most ripples are a single point.
- One signature sound or effect: none in the server or data half (client not read).
- Could be made ours at 20-30 percent resemblance: yes. "A reward to one faction moves a short list of linked factions by a multiplier, at least one point" transfers to a zone-wide reputation with the Pit and zone factions, and "everyone on the hate list is credited" transfers to many-vs-one.

## 3. The rule behind it
A. Ladder. Nine grades, each a minimum on the standing scale: ally, warmly, kindly, amiably, indifferently, apprehensively, dubiously, threateningly, scowls (`common/faction.h` lines 27-35). The minimums are rules (`common/ruletypes.h` lines 1065-1072). The grade is the first minimum the standing reaches, else the last grade (`common/faction.cpp` lines 57-88).
B. Ripple order (`zone/client.cpp` RewardFaction, lines 9107-9185). Step 1: the primary faction gets the full amount (line 9109). Step 2: the zone looks up the association row for that faction (line 9111). Step 3: each of up to 10 linked slots gets a value equal to its multiplier times the amount (the temporary-value block just above line 9156). Step 4: the sign of that value is kept (line 9156). Step 5: the magnitude is truncated to a whole number and raised to at least one point (line 9169). Step 6: each slot with a positive id gets its new value (the loop after line 9180). The ripple does not call itself again (the write goes to the set function, not to reward; set-function body not read).
C. Fan-out to the hate list. `HateList::DoFactionHits` (`zone/hate_list.cpp` lines 288-305) walks the NPC's hate list and calls RewardFaction on each client entry (line 303). Every player who fought, not only the killer, gets the hit. Caller that fires this on death not read.
D. Emote. Nine event types (`common/emu_constants.h` lines 334-344): leave combat, enter combat, on death, after death, hailed, killed a player, killed an NPC, on spawn, on despawn. A line is looked up by (emote id, event) (`zone/npc.cpp` lines 2752-2770). If several lines match, one is picked at random by the zone's roll (line 2767). Text tokens are replaced (line 2786 onward): the NPC clean name, race plural, race, class, class plural, and the target's clean name with a fallback word (line 2793).
E. Names. The cleaner turns underscores into spaces, keeps letters and the backtick, and drops digits, the hash sign and other punctuation (`common/strings_legacy.cpp` lines 214-232; the same rule in `common/database.cpp` lines 688-700). The mob caches the cleaned name the first time it is asked (`zone/mob.cpp` lines 5148-5154).
F. Start standing by race, class and deity. A faction has a base plus a min and max, and class, race and deity modifiers (`common/faction.h` FactionMods, line 48). The modifier table `faction_list_mod` (2023 file) holds 9801 rows across 556 faction ids and 49 modifier keys: 16 class keys (c1 to c16), 16 race keys (r1 to r12, r128, r130, r330, r522), and 17 deity keys (d201 to d216, d396). The key-prefix meanings are read from the names; the mapping from key to struct field was not read.
G. Race kinship. Two hard-coded functions say which races share a standing: equal race (`common/faction.cpp` line 91) and an indifferent-race group (line 112) with an in-code note that more values are to be added (lines 96 and 117).
H. Association data. `faction_association` is one row per source faction with up to 10 (linked faction, multiplier) pairs (`common/repositories/base/base_faction_association_repository.h`). The 2022 seed file has 371 rows; 122 rows have one filled slot, 87 two, 84 three, 62 four, and fewer above that.

Data fields (no donor values: GPL, and the numbers are game-derived):
- ladder_grades: unit grades; donor value null (9 grades in code).
- grade_min: unit standing points; donor value null (rule defaults exist; not copied).
- ripple_slots: unit slots; donor value null (10 in the schema).
- ripple_multiplier: unit multiplier (float); donor value null.
- ripple_min_step: unit points; donor value null (the code floors at 1).
- ripple_sign_source: rule; the product of amount and multiplier.
- fanout_scope: rule; "everyone on the hate list" (donor rule, shape only).
- emote_event_types: unit events; donor value null (9).
- emote_text_max: unit characters; donor value null (512 in the schema).
- clean_name_rule: rule; underscore to space, letters and backtick kept.
- start_modifier_keys: unit keys by race, class, deity; donor value null (49 in the 2023 file).

## 4. For Frankendom
Shape maps well. Many-vs-one: the hate-list fan-out is the right rule for a 3-attacker group. Every player who took part gets credit, and the server applies it to the one ledger. Zones as data: each zone can list which factions live there and the ripple table per faction (700 zones as data), so the same ripple code runs everywhere. Server-verified: the ripple and the fan-out must run on the server, and the client only shows the ladder word and the toast. Pit characters reuse the standing ladder across zones without new ladder code.
Keep: nine words (or the nine-step rule) as the standing card; one primary change plus a short linked list; the fan-out to everyone who took part; emote lines per combat event with name tokens; underscores in data names cleaned at display time.
Change, with the defect fixed in each case:
1. Zero multiplier still moves a linked faction. Code: `std::max(1, ...)` runs even when the value is zero, and the sign of zero is taken as positive (`zone/client.cpp` lines 9156 and 9169). Data: the 2022 seed has one such slot (line 16, slot 3: id 270 with multiplier 0). Fix: skip the slot when the multiplier is exactly zero (or when amount times multiplier is zero), and keep the one-point floor only for nonzero values.
2. Emote variety is dead under the shipped schema. Code picks randomly among several lines for one (emote id, event) (`zone/npc.cpp` line 2767), but the table has a unique key on (emote id, event) (`utils/sql/svn/2142_emotes.sql` line 8), so at most one line can exist. Fix: drop the unique key to (emote id, event, line id), keep the random pick, and add a seed so the roll is reproducible.
3. Threshold restore file is malformed. In `utils/sql/git/optional/2019_04_13_restore_legacy_faction_thresholds.sql` the kindly key is misspelled (line 5, "KindlyFactionMinimu", so the rule is never overridden), and rows on lines 7 to 9 lack the comma that joins them to the next row, so the statement will not parse. Fix: correct the key name, add the three commas, and test with the rule loader. Keep the idea: a documented way to set the nine minimums.
4. Outlier multipliers need a check, not a fix yet. Line 98 pairs a faction with a multiplier of 341 (slot 3) and carries a stray value of 1522 in an unused slot (slot 4, id 0). The id-0 slot is ignored by the positive-id guard, so it is harmless; the 341 is an outlier that would move a linked standing 341 times the amount. Ask the data owner whether it is a typo for a fraction. Negative ids (for example -4 on line 98, slot 5) are skipped by the same guard.
5. Rounding is truncation toward zero with a one-point floor. That is the design (a -0.05 rival still costs one point). Keep it, but expose the floor as a data field (ripple_min_step) so the designer can set 0 for quiet rivals.
6. Fan-out may run with no valid id. The branch in `zone/hate_list.cpp` (lines 297-305) calls the set function with the NPC faction id in the else case even when the id is not positive. Fix: guard the else branch on a positive id.

Ruling fit (parity checklist): row 18 (loot roll and XP award: the ripple is a reward step, and the fan-out is a reward to each participant), row 23 (zone population: the faction map is zone data, not engine logic), row 17 (the death and after-death emote is the death presentation). No engine row is changed by this note.

## 5. A 5-minute look test
In one zone, put a faction card on one Pit NPC with the nine-word ladder. Run three kills with a group of three. Show the ripple toast after each kill: one primary row, two or three linked rows, each showing its sign and point change. Compare two versions: (a) a one-point floor on every linked change, (b) a floor of zero for quiet rivals. On a 375-wide phone, judge whether the ladder word changes are readable at a glance and whether the toast rows fit without scrolling. Then compare emote lines: one line per event against three random lines per event.
