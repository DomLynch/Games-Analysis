Verdict reason: the only camera code is a fixed-position camera that looks along the +Z constant. Its yaw and pitch are computed in Rotate but never reach the view matrix, and the player is not followed, so the donor has no follow, orbit, shoulder, collision, lock-on or zoom mechanism to take.

Searches: grep -rn for camera, follow, zoom, orbit, look over the whole repo; the only camera logic is internal/camera/camera.go.

Findings:
- createViewMatrix (camera.go 53-65) uses graphic.Forward (transform.go 10, +Z), not c.front. So the yaw 270 and pitch -60 defaults (camera.go 18-19) and the front vector from Rotate (camera.go 89-93) do not change the picture.
- distance (30.0) and altitude (50.0) are set at construction (camera.go 43-44) and never read.
- UpdateVisibleZRange builds a view and discards it (camera.go 101-102).
- The keyboard moves the camera by 0.2 per pass of the loop (sdlclient 273), with no time base; the frame delta passed to the world is always zero (sdlclient 285-287), so this is not a usable clock for a camera.
- Sprite facing is computed against a fixed camera direction (character_render.go 28, 91), so sprites do not turn with a camera.

Best transferable idea: a third-person base only works when every angle the rig computes reaches the view matrix, so add a test that changing the stated yaw or pitch changes the rendered view, and fail the build when it does not.
Decision (proposed): reject — there is no follow mechanism here to adopt, the licence is copyleft (shape only), and the one lesson (dead angles and a discarded view) is covered by a test on our own camera, not by this code.
Side note (not camera, timing): sdlclient main.go 285 computes the delta as frameStart.Sub(frameStart), so any world update in that loop gets dt 0.
