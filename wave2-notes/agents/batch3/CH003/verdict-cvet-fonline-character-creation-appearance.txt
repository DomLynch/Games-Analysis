What the donor has:
- A bake-time colour layer. A sprite's filename may carry bracket entries "[part,r,g,b]" (ImageBaker.cpp 1682, format comment). Part 0 other, 1 skin, 2 hair, 3 armor (1679). Each part has its own RGB offset, default zero (1680). Part 0-3 sets that part; any other part index sets all parts (1716).
- Compose: for each of the four parts in order (1957), each pixel colour is taken from palette[part] (2032), each channel with a non-zero offset is shifted and clamped to 0..255 (2048-2051), then part 0 writes every pixel (2057) and parts 1-3 write only pixels with alpha >= 128 (2060).
- Docs confirm the same (image-format.md 253-254).

What the donor does NOT have:
- No character creation UI, no body family, no face, no scar, no name rule, no class choice. The only creation word is an error code, NetWrongTagSkill = 1029 ("Identifies character creation rejected because the required tagged-skill selection is invalid", Common.h 434); nothing in Source uses it (grep).
- Login: LoginPlayerToNewRecord stores the new player record (Server.cpp 3120), then fires OnPlayerLogin (3128). What the new character looks like is decided by the game script on that event. The engine does not create the critter's look.

Why PARTIAL and not STRONG: the one real mechanism is a bake-time colour shift for three palette layers (skin, hair, armor). It is real and read end to end, but it is a colour fragment, applied when the sprite is baked from a filename, so a player's skin or hair cannot be changed at runtime by this code. It does not cover body families, faces, scars or creation order.
